Idempotency keys: making retries safe

The small header that stops a timeout from charging someone twice, with a FastAPI implementation you can run.

Hoang-Vu Le · Nov 1, 2026 · 8 min read

A client sends POST /payments and the connection dies before the response arrives. Did the payment happen? The client cannot know, so it does the only sensible thing and retries. If the server treats the retry as a brand-new request, the customer is charged twice.

The same shape shows up everywhere there is a retry loop: a mobile app on a flaky network, a message queue with at-least-once delivery, and, increasingly, an agent orchestrator that re-runs a failed step, which re-runs every tool call inside it. The fix is old and boring, which is why I like it. This is general backend knowledge rather than anything specific to one codebase.

The contract

An operation is idempotent if doing it twice has the same effect as doing it once. PUT and DELETE are idempotent by definition; POST is not. An idempotency key makes a POST behave as if it were:

  1. The client generates a unique key per logical operation (a UUID, or something like order-123-attempt), and sends it in an Idempotency-Key header. The same key is reused on every retry of that operation, and never for a different one.
  2. The server remembers the key together with the result. If the key shows up again, it returns the stored result instead of doing the work again.

This is a widely copied convention. Stripe’s API accepts an Idempotency-Key header and replays the saved result for a repeated key, and there is an IETF draft that tries to standardise the header. I am only relying on that general shape here, so check the current docs for details such as key length and expiry.

Four cases the server must handle

  1. Key never seen: Claim it, do the work, store the result, return it.
  2. Key seen, work finished, same body: Return the stored status and body again, marked as a replay.
  3. Key seen, work still running: 409 Conflict with Retry-After. Do not start a second copy.
  4. Key seen, different body: 422. The client has a bug; refusing loudly beats silently ignoring its new request.

The third row is the one people forget. Two identical requests arriving at nearly the same time are the common retry pattern, not an edge case, so “check if the key exists, then insert it” is a race. Claiming the key has to be a single atomic step.

A FastAPI implementation

Here is a compact version with an in-memory store, so it runs anywhere. The store’s claim method is the atomic step; the endpoint is a thin state machine around it.

import hashlib, json, threading, time, uuid
from fastapi import FastAPI, Header, HTTPException, Response
from fastapi.encoders import jsonable_encoder
from pydantic import BaseModel

app = FastAPI()
TTL_SECONDS = 24 * 3600

class PaymentIn(BaseModel):
    customer_id: str
    amount: int          # minor units, e.g. cents
    currency: str

class IdempotencyStore:
    """In-memory stand-in. In production: Redis (SET NX EX) or a unique index."""
    def __init__(self):
        self._rows, self._lock = {}, threading.Lock()

    def claim(self, key, fingerprint):
        now = time.time()
        with self._lock:                       # atomic check-and-insert
            row = self._rows.get(key)
            if row and row["expires"] > now:
                if row["fingerprint"] != fingerprint:
                    return "mismatch", row
                return ("replay" if row["done"] else "in_flight"), row
            row = {"fingerprint": fingerprint, "done": False,
                   "status": None, "body": None, "expires": now + TTL_SECONDS}
            self._rows[key] = row
            return "new", row

    def finish(self, key, status, body):
        with self._lock:
            self._rows[key].update(done=True, status=status, body=body)

    def release(self, key):
        with self._lock:
            self._rows.pop(key, None)

store = IdempotencyStore()

def charge_card(p: PaymentIn) -> dict:          # stand-in for the payment provider
    return {"id": f"pay_{uuid.uuid4().hex[:8]}", "amount": p.amount, "status": "succeeded"}

@app.post("/payments", status_code=201)
def create_payment(body: PaymentIn, response: Response,
                   idempotency_key: str = Header(..., min_length=8, max_length=255)):
    fingerprint = hashlib.sha256(
        json.dumps(jsonable_encoder(body), sort_keys=True).encode()).hexdigest()
    outcome, row = store.claim(idempotency_key, fingerprint)

    if outcome == "mismatch":
        raise HTTPException(422, "Idempotency-Key already used with a different body")
    if outcome == "in_flight":
        raise HTTPException(409, "Request with this key still in progress",
                            headers={"Retry-After": "1"})
    if outcome == "replay":
        response.status_code = row["status"]
        response.headers["Idempotent-Replayed"] = "true"
        return row["body"]

    try:                                       # outcome == "new": we own the key
        result = charge_card(body)             # the side effect
    except Exception:
        store.release(idempotency_key)         # nothing committed: allow a retry
        raise
    store.finish(idempotency_key, 201, result)
    return result

Three details worth pointing out. The fingerprint is a hash of the canonicalised body (sorted keys), which is what lets the server tell “same request again” from “same key, different request”. The header name is Idempotency-Key; FastAPI maps the parameter idempotency_key to it automatically. And the key should be scoped, per user or tenant, in a real system, otherwise one customer’s key can collide with another’s.

Does it actually work?

I ran it through an ASGI test client, with charge_card sleeping for 200 ms and appending to a list so I could count charges:

  • Same key and body sent twice in sequence: the second call returned the identical body with Idempotent-Replayed: true, and the list held one charge.
  • Same key, amount changed from 1000 to 999: 422.
  • Five identical requests fired concurrently: exactly one 201 and four 409 with Retry-After: 1, and one charge in total.

That is a single-process test. The lock only protects one process, which is precisely why the next section matters.

Moving it out of memory

With more than one server process, the atomic claim must live in shared storage. Two common options:

  • Redis: SET idem:{tenant}:{key} "{fingerprint}:in_flight" NX EX 86400. NX makes the set succeed only if the key is absent, and EX gives you the TTL for free. On completion, overwrite the value with the result.
  • Postgres: a table with a unique constraint, claimed by an insert that does nothing on conflict. If one row was inserted, you own the key; otherwise read the existing row.
CREATE TABLE idempotency_keys (
  tenant_id     text        NOT NULL,
  key           text        NOT NULL,
  fingerprint   text        NOT NULL,
  status        text        NOT NULL DEFAULT 'in_flight',
  response_code int,
  response_body jsonb,
  expires_at    timestamptz NOT NULL,
  PRIMARY KEY (tenant_id, key)
);

INSERT INTO idempotency_keys (tenant_id, key, fingerprint, expires_at)
VALUES ($1, $2, $3, now() + interval '24 hours')
ON CONFLICT DO NOTHING;   -- 1 row affected = you own it

If the payment row itself also lives in Postgres, write it and mark the idempotency record done in the same transaction. Then a crash can never leave one without the other.

The sharp edges

  • The crash window. If the process dies after charge_card but before finish, the key is stuck in_flight until it expires, and the retry gets 409s. For external side effects, pass a key derived from the client’s key to the downstream provider too, so the provider deduplicates as well. Idempotency has to hold at every hop, not just yours.
  • Should failures be stored? I release the key on an exception so the client may retry. That is right for “nothing happened” errors. If a failure is ambiguous (a timeout after the provider may have acted), it is safer to keep the key claimed and reconcile later. Some APIs store the first result, errors included, so decide deliberately.
  • TTL. A day is typical. It must outlast your clients’ longest retry window, and it bounds how much you store.
  • Client-side discipline. A key per attempt instead of per operation defeats the whole scheme. Generate the key once, before the first try, and persist it.

Why I care about this for agents

An LLM agent calling tools is a retry-heavy system by nature: models time out, rate limits bite, orchestrators resume from a checkpoint. If a step that already created a ticket, sent an email or charged a card is replayed, the tool call runs again. Giving each side-effecting tool call a stable key (for example derived from the run id and step id) means a replay becomes a no-op instead of a duplicate. Read-only calls need no key; anything that writes does.

Takeaway. An idempotency key turns “retry and hope” into “retry safely”. Claim the key atomically, store the result, fingerprint the body, return 409 for in-flight duplicates, and make the guarantee hold at every hop, not just at your edge.
